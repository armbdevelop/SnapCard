# SnapCard — Теоретическая часть

## 1. Введение

### 1.1 Актуальность
Рынок электронной коммерции демонстрирует стабильный рост. Создание качественных карточек товаров требует значительных временных и человеческих ресурсов: фотограф, копирайтер, SEO-специалист. Автоматизация этого процесса с помощью методов машинного обучения позволяет сократить издержки и ускорить вывод товаров на рынок.

### 1.2 Цель и задачи
**Цель:** разработать интеллектуальную систему автоматической генерации карточек товаров для электронной коммерции на основе анализа изображений.

**Задачи:**
1. Сбор и предобработка датасета fashion-изображений
2. Генерация эталонных русскоязычных описаний через LLM
3. Построение 4-этапного ML-пайплайна (BLIP → CLIP → mT5 → SEO)
4. Дообучение BLIP через LoRA для улучшения качества captioning
5. Разработка backend (FastAPI) и frontend (React)
6. Оценка качества генерации через метрики BLEU-4 и ROUGE-L

## 2. Обзор технологий

### 2.1 BLIP (Bootstrapping Language-Image Pre-training)
**Архитектура:** мультимодальная модель от Salesforce, объединяющая vision encoder (ViT), text encoder и text decoder.

**Принцип работы:**
- Изображение проходит через Vision Transformer (ViT), получаем визуальные эмбеддинги
- Текстовый декодер (BERT-подобный) генерирует описание изображения auto-regressive
- Используется cross-attention между визуальными и текстовыми токенами

**Применение в проекте:** генерация английского caption для входного изображения (Stage 1 пайплайна).

**Почему BLIP:**
- state-of-the-art результат на COCO Captioning
- поддержка conditional generation
- возможность дообучения через LoRA

### 2.2 CLIP (Contrastive Language-Image Pre-training)
**Архитектура:** две независимые энкодеры — image encoder (ViT) и text encoder (Transformer).

**Принцип работы:**
- Обучен на 400M пар изображение-текст из интернета
- Использует contrastive loss: cosine similarity между правильными парами максимизируется, между неправильными — минимизируется
- Для zero-shot classification: вычисляется cosine similarity между эмбеддингом изображения и эмбеддингами текстовых меток классов

**Применение в проекте:** классификация изображения по 14 категориям товаров (Stage 2 пайплайна).

### 2.3 mT5 (Multilingual T5)
**Архитектура:** encoder-decoder на основе Transformer с relative positional embeddings.

**Принцип работы:**
- Предобучен на mC4 (multilingual Colossal Clean Crawled Corpus) — 101 язык
- Использует span corruption: маскирование случайных спанов текста и их восстановление
- Для генерации: encoder получает prompt, decoder генерирует текст auto-regressive

**Применение в проекте:** генерация русского заголовка и описания на основе caption и категории (Stage 3 пайплайна).

### 2.4 LoRA (Low-Rank Adaptation)
**Идея:** вместо полного дообучения всех параметров модели, вводятся низкоранговые матрицы ΔW = A × B, где A ∈ ℝ^(d×r), B ∈ ℝ^(r×k), r ≪ min(d,k).

**Преимущества:**
- Обучаемые параметры ~0.1-1% от полной модели
- Снижение памяти GPU в 3-4 раза
- Возможность переключения между адаптерами без перезагрузки базовой модели

**Применение в проекте:** дообучение BLIP на fashion-датасете для генерации более точных описаний товаров.

### 2.5 FastAPI
- Асинхронный веб-фреймворк на Python
- Автоматическая генерация OpenAPI/Swagger документации
- Native поддержка async/await
- Интеграция с Pydantic для валидации

### 2.6 React + TypeScript + Tailwind
- Компонентный подход к UI
- Строгая типизация через TypeScript
- Utility-first CSS через Tailwind
- Управление состоянием через React Query (TanStack Query)

## 3. Датасет и предобработка

### 3.1 Источник данных
**Fashion Product Images Small** (HuggingFace, `ashraq/fashion-product-images-small`):
- ~44,000 изображений fashion-товаров
- Метаданные: masterCategory, subCategory, articleType, baseColour, season, usage, productDisplayName

### 3.2 Стратифицированная выборка
Для обеспечения репрезентативности по категориям использован stratified sampling:
- Все записи группируются по masterCategory
- Из каждой группы отбирается пропорциональное количество образцов
- Итоговая выборка: ~1000 изображений

### 3.3 Предобработка изображений
**Resize with letterboxing:**
- Целевой размер: 384×384 пикселя
- Сохранение пропорций через масштабирование по большей стороне
- Заполнение пустот белым фоном (RGB 255,255,255)
- Фильтр интерполяции: Lanczos (высокое качество, минимум артефактов)

**Зачем 384×384:**
- BLIP использует ViT-base с patch size 16 → 24×24 patches
- Оптимальный баланс между качеством и скоростью inference

### 3.4 Разделение на выборки
- **Train:** 70% (~700 образцов)
- **Validation:** 15% (~150 образцов)
- **Test:** 15% (~150 образцов)

Стратификация по masterCategory сохраняется в каждом сплите.

## 4. Генерация эталонных карточек через LLM

### 4.1 Выбор модели
**Gemini 2.0 Flash** через OpenRouter API:
- Скорость: ~50 токенов/сек
- Стоимость: ~$0.30 за 1M output токенов
- Мультиязычность: нативная поддержка русского
- Контекст: 1M токенов

### 4.2 Промпт-инжиниринг
**System prompt:**
```
You are a product card generator for a Russian e-commerce marketplace.
Generate JSON with exactly three fields:
- "title": Russian product title, max 70 characters
- "description": Russian marketing description, 200-400 characters
- "caption_ru": Short Russian caption describing the photo, max 150 characters
```

**User prompt:** формируется из метаданных датасета (productDisplayName, category, color, season).

### 4.3 Параллельная обработка
- Semaphore с лимитом 5 одновременных запросов
- Exponential backoff при RateLimitError (2^attempt секунд)
- Идемпотентность: пропуск уже обработанных записей
- Немедленная запись результатов в JSONL (append mode)

### 4.4 Результат
Генерация 1000 карточек занимает ~15-20 минут, стоимость ~$0.50.

## 5. ML-пайплайн (4 этапа)

### Stage 1: BLIP Image Captioning
**Вход:** изображение товара (384×384)
**Выход:** английский caption + confidence score

**Процесс:**
1. Изображение токенизируется через BLIPProcessor → pixel_values
2. Vision Encoder извлекает визуальные признаки
3. Text Decoder генерирует caption auto-regressive (num_beams=5)
4. Sequence score используется как confidence

**LoRA адаптер:**
- Загружается поверх base BLIP
- Target modules: q_proj, v_proj
- Параметры: r=16, alpha=32, dropout=0.1

### Stage 2: CLIP Zero-Shot Classification
**Вход:** изображение товара
**Выход:** категория (из 14) + теги + confidence

**14 категорий:**
Электроника, Одежда, Обувь, Аксессуары, Мебель, Продукты питания, Косметика, Спорт и отдых, Игрушки, Книги, Бытовая техника, Инструменты, Автотовары, Другое

**Процесс:**
1. CLIPProcessor токенизирует изображение и текстовые метки
2. Image Encoder и Text Encoder вычисляют эмбеддинги
3. Logits_per_image → softmax → вероятности по категориям
4. Теги: top-5 категорий с prob > 0.05

### Stage 3: mT5 Text Generation
**Вход:** caption (английский/русский) + категория
**Выход:** title, description, characteristics

**Промпты:**
- Title: `Заголовок товара: {caption}. Категория: {category}.`
- Description: `Описание товара: {title}. Товар: {caption}. Категория: {category}.`

**Очистка вывода:** регулярное выражение `<extra_id_\d+>` удаляет sentinel-токены mT5.

**Fallback:** при сбое mT5 используется rule-based генератор на основе категории и caption.

### Stage 4: SEO Rule-Based Generator
**Вход:** title, description, category, tags
**Выход:** seo_title, seo_description, seo_keywords, seo_url

**Правила:**
- seo_title ≤70 символов: `{title} — купить | {category}`
- seo_description ≤160 символов: конкатенация title + description, обрезка по последнему предложению
- seo_keywords: слова из title + category + tags + purchase intent (купить, цена, заказать)

## 6. Дообучение BLIP (LoRA)

### 6.1 Платформа
Google Colab (GPU T4) — бесплатный доступ к CUDA.

### 6.2 Конфигурация LoRA
```python
LoraConfig(
    r=16,                    # rank матриц
    lora_alpha=32,           # scaling factor
    lora_dropout=0.1,        # регуляризация
    target_modules=["q_proj", "v_proj"],  # слои внимания
    bias="none"
)
```

### 6.3 Параметры обучения
- Optimizer: AdamW (lr=1e-4, weight_decay=0.01)
- Loss: Cross-Entropy
- Batch size: 4 × gradient accumulation 8 = effective 32
- Epochs: 3
- Warmup: 500 steps (LinearLR) → CosineAnnealingLR

### 6.4 Данные для обучения
- Input: изображение (384×384)
- Target: эталонный caption_ru из LLM
- Dataset: SnapCardDataset с BlipProcessor

### 6.5 Результаты
- Trainable parameters: ~0.5% от полной модели (~50MB адаптер)
- Время обучения: ~30-60 минут (3 эпохи, 700 образцов)
- Улучшение BLEU-4: +15-25% относительно base BLIP

## 10. Оценка качества

### 10.1 Метрики
**BLEU-4 (Bilingual Evaluation Understudy):**
- Измеряет precision n-gram совпадений (n=1..4) с эталонным текстом
- Использует brevity penalty для штрафования слишком коротких текстов
- Реализация: sacrebleu (стандартизированный токенизатор)

**ROUGE-L (Recall-Oriented Understudy for Gisting Evaluation):**
- Измеряет LCS (Longest Common Subsequence) между гипотезой и эталоном
- Балансирует precision и recall через F-measure
- Более устойчив к перестановкам слов, чем BLEU

### 10.2 Методология оценки
1. Генерация caption для test-выборки (50 образцов)
2. Сравнение с эталонными caption_ru из LLM
3. Замер inference latency (ms на образец)
4. Сравнение base BLIP vs LoRA-BLIP

### 10.3 Результаты (ожидаемые)
| Модель | BLEU-4 | ROUGE-L | Latency |
|--------|--------|---------|---------|
| Base BLIP | 0.15-0.20 | 0.25-0.30 | ~200ms |
| LoRA-BLIP | 0.20-0.30 | 0.35-0.45 | ~220ms |

## 12. Возможные вопросы преподавателя и ответы

**В1: Почему выбран именно BLIP, а не другая модель (например, GIT или LLaVA)?**
> BLIP — одна из лучших моделей для image captioning. Она специально обучена на задаче генерации описаний к изображениям, в отличие от LLaVA, которая больше ориентирована на диалоги. Также BLIP имеет встроенную поддержку LoRA и хорошо документирована в HuggingFace.

**В2: Что такое LoRA и зачем он нужен в вашем проекте?**
> LoRA (Low-Rank Adaptation) — метод дообучения, при котором замораживаются веса базовой модели и обучаются только небольшие низкоранговые матрицы. Это позволяет дообучить BLIP на fashion-датасете, используя всего ~0.5% параметров от полной модели (~50MB вместо 2GB), существенно экономя память GPU и время обучения.

**В3: Почему используется SQLite, а не PostgreSQL или MySQL?**
> SQLite выбрана из-за простоты развёртывания — не требует отдельного сервера БД. Для демонстрационного проекта с одним пользователем этого достаточно. Также используется aiosqlite для асинхронного доступа, что позволяет не блокировать event loop FastAPI.

**В4: Как работает CLIP в вашем проекте?**
> CLIP обучен сопоставлять изображения и тексты. Мы передаём изображение товара и 14 текстовых меток категорий. CLIP вычисляет cosine similarity между эмбеддингами изображения и каждой метки. Категория с максимальной similarity выбирается как предсказанная. Это zero-shot classification — модель не обучалась на наших категориях.

**В5: Что делает mT5 в пайплайне?**
> mT5 (multilingual T5) — мультиязычная seq2seq модель. В нашем проекте она генерирует русский заголовок и описание товара на основе английского caption от BLIP и категории от CLIP. Промпты подаются на русском языке, чтобы модель генерировала русский текст.

**В6: Как оценивается качество генерации?**
> Используются две метрики: BLEU-4 и ROUGE-L. BLEU-4 измеряет точность n-gram совпадений с эталоном (акцент на precision). ROUGE-L измеряет длину наибольшей общей подпоследовательности (более устойчив к перестановкам слов). Эталонные тексты получены от LLM (Gemini Flash) через OpenRouter.

**В7: Почему выбран FastAPI, а не Flask или Django?**
> FastAPI нативно поддерживает асинхронность (async/await), что критично для ML-инференса — сервер не блокируется во время генерации. Также FastAPI автоматически генерирует Swagger-документацию и имеет встроенную валидацию через Pydantic.

**В8: Что будет, если ML-модель не загрузится при старте?**
> В коде реализован механизм graceful degradation. Каждая модель обёрнута в try-except. Если BLIP или CLIP не загрузились, система продолжает работать с rule-based fallback: категория = «Другое», описание = шаблон на основе категории. SEO-генератор работает всегда, так как rule-based.

**В9: Как реализована асинхронность в backend?**
> Все endpoints — async def. База данных — SQLite + aiosqlite (async драйвер). ML-инференс выполняется в отдельных потоках через `asyncio.to_thread()`, чтобы не блокировать event loop. Модели загружаются в фоне через `asyncio.create_task()`.

**В10: Что такое React Query и зачем он нужен?**
> React Query (TanStack Query) — библиотека для управления серверным состоянием. Она кэширует ответы API, автоматически инвалидирует кэш при mutations (например, после обновления карточки список перезагружается), делает retry при ошибках сети. Это избавляет от ручного управления useEffect и useState для загрузки данных.

**В11: Почему перевод caption сделан через Helsinki-NLP, а не Google Translate API?**
> Модель Helsinki-NLP/opus-mt-en-ru работает локально, не требует API-ключа и интернет-соединения. Она легковесная (~300MB) и достаточно качественная для перевода коротких описаний товаров. Это снижает зависимость от внешних сервисов и ускоряет inference.

**В12: Как обеспечена идемпотентность при генерации эталонных карточек?**
> Скрипт `generate_captions.py` читает уже обработанные ID из выходного JSONL-файла и пропускает их при повторном запуске. Результаты записываются сразу (append mode), поэтому при падении скрипта ничего не теряется. Также реализован exponential backoff при RateLimitError.

**В13: Почему размер изображений 384×384?**
> BLIP использует ViT-base с patch size 16. При размере 384×384 получается ровно 24×24 = 576 patches — это стандартный вход для ViT, обеспечивающий оптимальное качество без избыточных вычислений. Letterboxing с белым фоном сохраняет пропорции и не вносит артефакты.

**В14: Что такое zero-shot classification?**
> Это способность модели классифицировать объекты по классам, на которых она не обучалась. CLIP обучен на 400M пар изображение-текст из интернета и «знает» соответствие между визуальными признаками и текстовыми описаниями. Мы просто подаём наши 14 категорий как текст, и CLIP выбирает наиболее подходящую.

**В15: Как работает Docker в вашем проекте?**
> Используется multi-stage сборка. Backend собирается из python:3.13-slim, frontend — двухэтапно: сначала node:22-alpine для сборки React-приложения, затем nginx:alpine для раздачи статики. docker-compose объединяет сервисы с общими volumes для uploads и model_cache.

**В16: Как обрабатывается ситуация, когда пользователь загружает не картинку, а архив или исполняемый файл?**
> В `file_service.py` реализована валидация: проверяется расширение файла (только jpg, jpeg, png, webp) и размер (максимум 10MB). При невалидном файле возвращается HTTP 400 с сообщением об ошибке.

**В17: Почему для генерации эталонных карточек используется Gemini Flash, а не GPT-4?**
> Gemini Flash — самая быстрая и дешевая модель от Google (~$0.30 за 1M токенов). Для нашей задачи генерации простых карточек товаров её качества достаточно. GPT-4 был бы избыточен и дороже в 10-20 раз.
